## 1. Goal

Windows 10/11 with Docker Engine in WSL2 stays the **primary** production host (`deploy-init-plan.md`). This plan adds an **alternative**: the same stack on a Linux machine or a Mac, if the station ever needs it, and on the way splits the deploy repository into:

- a **common core** that runs the same everywhere (all application and infrastructure containers, `radioctl`'s logic, backups, restore drill, boot check, update, rollback, maintenance, cut-over), and
- a **thin host layer** per platform: what is needed only to get Docker running, start it at boot, and call the core (`install.bat`/`update.bat` on Windows; `install.sh`/`update.sh` on Linux and macOS).

Everything stays in Docker; nothing of the application runs natively on the host. The shape is chosen so a later move to Kubernetes maps one to one (§8).

## 2. Decisions (2026-11-14)

1. **Apps in Docker on every host.** The host provides only a Docker engine. Linux: Docker Engine. macOS: **Colima** (free, headless, started by launchd; Docker Desktop and OrbStack were considered: Desktop needs a signed-in user, OrbStack is paid for commercial use).
2. **The core moves into an ops container.** `radioctl` and its tools (bash 5, jq, git, coreutils, curl, Docker CLI and Compose plugin) run in a pinned image `radio-atlantida-ops`, started with the host's Docker socket. The host needs no bash version, jq, or GNU tools of its own (macOS ships bash 3.2 and BSD tools).
3. **Scheduled jobs move into the stack.** A `scheduler` compose service (the ops image with supercronic) runs `radioctl backup` daily at 04:30 and `radioctl restore-drill` at 05:30 on the 1st, in `Asia/Yerevan` (as the systemd timers do now), and `radioctl boot-check` once when it starts. This replaces the systemd timers on Linux and macOS; in Kubernetes it becomes CronJobs.
4. **Linux first**, then macOS. Linux can be tested end to end in CI (§7); macOS only by a manual dry run.
5. **Windows unchanged by this plan.** U0 refactors without changing behaviour (bats and Pester stay green). Moving Windows onto the ops container and scheduler too is a possible later step (§9), not part of this plan.
6. **Linux distributions.** The installer installs Docker Engine (pinned in `install/versions.env`) on Ubuntu 24.04 LTS and Debian 12/13; on any other distribution it requires Docker Engine ≥ the pinned version to be installed already and checks it (confirmed 2026-11-14).
7. **Database location per platform.** Linux: the bind-mounted directory `/srv/radio/pgdata` (6.11). macOS: a named volume inside Colima's VM, because a bind mount from the macOS file system goes through virtiofs, which is slow and unreliable for PostgreSQL's `fsync` and permissions; the dumps are copied to a folder on the Mac (the counterpart of the Windows copy).

## 3. What is common and what is per host

| Part | Common core | Windows (primary, unchanged) | Linux | macOS (Colima) |
|---|---|---|---|---|
| Containers (`docker-compose.yml`) | all services, pins, health checks | — | — | — |
| `radioctl` logic | update, rollback, restore, maintenance, cut-over, status, backup, restore drill, boot check | runs in WSL bash (as now) | runs in the ops container | runs in the ops container |
| Platform facts (`bin/lib/platform/*.sh`) | interface | `wsl.sh` | `linux.sh` | `macos.sh` |
| Docker engine | — | Docker Engine in WSL (`install.ps1`, `setup-distro.sh`) | Docker Engine (`install.sh`) | Colima (`install.sh`) |
| Start at boot | `restart: unless-stopped` | Task Scheduler + keep-alive | `systemctl enable docker` | launchd daemon starts Colima |
| Schedules | backup, restore drill, boot check | systemd timers in WSL (as now) | `scheduler` service | `scheduler` service |
| Database | PostgreSQL 17 | `/srv/radio/pgdata` in WSL (6.11) | `/srv/radio/pgdata` | named volume in Colima's VM |
| Second backup copy | `BACKUP_COPY_DIR` (renamed from `BACKUP_WINDOWS_COPY`, old name still read) | `C:\RadioAtlantida\backups` | a path on another disk, or empty | a folder on the Mac |
| Media | `MEDIA_ROOT` | `D:\…` via `/mnt/d` | any host folder | a folder under a Colima mount |
| Live voice UDP | `LIVE_UDP_BIND`, `LIVE_PUBLIC_IPS` | NAT or mirrored (`radioctl network`) | `127.0.0.1` | `127.0.0.1` through Colima's `grpc` port forward (built, to verify, 5.3) |
| Entry points | — | `install.bat`, `update.bat` | `install.sh`, `update.sh` | `install.sh`, `update.sh` |
| Host hardening | — | `install.ps1` (sleep, updates, active hours) | none required (a server distribution) | `pmset`: no sleep, `autorestart 1` after a power loss; auto login of a dedicated user is not needed with launchd |

## 4. The ops container

- **Image.** `ops/Dockerfile` in this repository (a deliberate exception to "no build steps": it is tooling, not application code), Debian slim + bash, jq, git, curl, tzdata, Docker CLI and Compose plugin at the versions pinned in `install/versions.env`, supercronic. Built for `linux/amd64` and `linux/arm64` by this repository's CI on a tag `ops-vX.Y.Z`, pushed to `ghcr.io/astronin/radio-atlantida-ops`, and pinned by digest in `ops.env` (like `release.env`). The image holds tools only; the deploy repository stays a checkout on the host, so `git pull` keeps working as the update source of `radioctl`.
- **Same paths inside and outside.** Compose resolves bind-mount sources on the host, while `radioctl` reads the same files from inside the container. So every host path the stack uses is mounted at the **same path** in the ops container: the deploy checkout (`/opt/radio-atlantida/deploy`), `/srv/radio` (journal, backups, pgdata on Linux), `MEDIA_ROOT` (read-only), and `BACKUP_COPY_DIR`. On macOS these paths are under a Colima mount (the default mounts the user's home; the installer adds the deploy and data folders explicitly).
- **Docker socket.** `/var/run/docker.sock` is mounted into the ops container and the `scheduler`. Access to the socket is root on the host; acceptable here because the stack is local only, nothing in the ops container listens on a port, and the image is pinned by digest. Written down in the runbook.
- **Typed confirmations.** `update.sh` runs the container with `-it` when a terminal is attached, so `CUTOVER`, `MAINTENANCE`, `RESTORE` work as on Windows; the `scheduler` runs only non-interactive commands.
- **Identity and files.** The container runs as the host's `radio` user id (Linux) or the installing user (macOS), so files in the checkout and in `/srv/radio` keep their owners; the Docker group id is passed for the socket.

### 5.1 U0 and U1 as implemented (deviations)

- **Platform default.** `RADIOCTL_PLATFORM` unset means `wsl` whether or not `WSLInterop` exists: the Mac dry-run VM and the bats container run the Windows path without it; `bin/radioctl-ops` always sets the platform (`linux`/`macos` from `uname`). An unknown value stops with exit 2.
- **Platform interface.** `bin/lib/platform/<p>.sh` defines `PLATFORM_*` values (entry points `install.bat`/`update.bat` or `install.sh`/`update.sh`, the copy label "Windows copy"/"backup copy", what writes `network.env`, what runs the schedules, the uptime label, the network modes, the usage lines) and `platform_*` functions (`host_path`, `copy_missing_msg`, `network_mode`, `uptime`, `local_url`, `disk_paths`, `media_status`, `check_schedules`, `side_logs`); `macos.sh` sources `linux.sh` and overrides. The Windows wording is unchanged byte for byte.
- **Network on Linux and macOS:** a mode `local` (both values 127.0.0.1) that `radioctl network` writes to `runtime/network.env` when it differs, instead of a pure no-op (U3 step 3), so the installer and the scheduler need no other writer; `--mode nat` is refused there (U4 adds it on macOS if Colima needs it).
- **Media status on Linux** reads the folder's group (10001) and group-write bit instead of `-w`, because the ops container mounts the media read-only; macOS checks presence only (Colima's mount does not show owners).
- **`BACKUP_COPY_DIR` vs the old name:** the new name wins when the key exists, even empty (an empty value disables the copy). The state key `last_backup.windows_copy` keeps its name on every platform.
- **Ops image pins:** the base image (Debian trixie slim by index digest) and supercronic (v0.2.51, SHA-256 per architecture) are in `ops/versions.env`, not `install/versions.env`, so `install.ps1`'s version comparison is untouched. The Docker CLI, Compose, and buildx are the `install/versions.env` versions built for Debian (`5:29.9.3-1~debian.13~trixie`), from Docker's signed Debian repository with the pinned key fingerprint; buildx is included because `radioctl` resolves digests with it.
- **Release workflow:** `ci.yml` builds and smoke tests the image on every push and PR (job `ops`, native amd64 and arm64 runners); the push lives in a separate `.github/workflows/ops-release.yml` on tags `ops-vX.Y.Z` (check, per-arch build + smoke + push by digest, manifest list), whose summary prints the `ops.env` values. Not yet run on GitHub.
- **`radioctl-ops` details:** registry logins of `radioctl` go to `DOCKER_CONFIG=<checkout>/runtime/docker` (not the host user's `~/.docker`, whose credential helpers, e.g. macOS keychain, do not exist in the container); the container is `--read-only` with a tmpfs `/tmp`, `--init`, `no-new-privileges`; the socket's group id is read with `stat` on Linux and through the image on macOS; root is refused; a missing path is not mounted (Docker would create it); the media folder is mounted read-only even inside a read-write parent. `RADIOCTL_OPS_IMAGE` selects a local build until `ops.env` has a digest; without either it stops with a clear message (since the Linux dry run it uses the local build `radio-atlantida-ops:local` by itself when that exists, 5.2).
- **Decided (2026-11-14):** the GHCR package `radio-atlantida-ops` is public (it holds only public tools and this public repository's scripts, no secrets), so a fresh host can pull it before any login. Set the package visibility to public on GitHub once, after the first `ops-v1.0.0` tag. The backend and frontend packages are unchanged (pulled with `GHCR_READ_TOKEN`).

### 5.2 U2 and U3 as implemented (deviations)

- **The scheduler's host part is generated.** `docker-compose.yml` holds the fixed part of `scheduler` (profile, `restart: unless-stopped`, `pull_policy: missing`, `init`, read-only with a tmpfs `/tmp`, `no-new-privileges`, `network_mode: none`, `TZ=Asia/Yerevan`, `RADIOCTL_SCHEDULER=1`). The host part (image, user, socket group, platform, `DOCKER_CONFIG`, entrypoint, working directory, the same-path mounts and the socket) is `runtime/scheduler.yml`, written by `bin/radioctl-ops` at every run (only when it changed) from the very values of the ops container, so the two never differ; mounts of empty or missing paths are left out, which Compose variables cannot do. `radioctl` adds `-f runtime/scheduler.yml --profile scheduler` to every compose call when `PLATFORM_SCHEDULER=true` (linux, macos) and the file exists; Windows never has the file.
- **Networks.** The scheduler has no network (it reaches the stack through the socket). The ops container now uses the host network: `docker buildx imagetools inspect` runs in the client, so registries and `127.0.0.1` (the test registry) must be what the host sees, as for `radioctl` in WSL; nothing in it listens.
- **Start sequence** (`bin/radioctl-scheduler`, detached from supercronic so the schedule starts at once): `radioctl boot-check` only when the host (macOS: Colima's VM) booted at most 15 minutes ago (`RADIOCTL_SCHEDULER_BOOT_WINDOW`, default 900 s). The plan said "once at start"; a recreate by an update or a restarted engine is not a boot and would record a misleading `LATE` result as the last boot check. Then `radioctl backup --catch-up`: a new option that decides before the lock and the run log (a backup that is not due leaves no log) and skips a machine without an installed release (the first run makes its own first backup).
- **Commands refused in the scheduler:** under `RADIOCTL_SCHEDULER=1` radioctl runs only `backup`, `restore-drill`, `boot-check`, `status`, `logs` and exits 2 otherwise (§6). The crontab sets `RADIOCTL_LOCK_WAIT=3600` like the systemd units.
- **Lifecycle:** the first run starts the scheduler before the first backup (`platform_check_schedules` on linux/macos: `compose up`, then the state must be `running`, else a warning); `update` and `rollback` have a step "Scheduler service" (`compose up`, which recreates it only when its definition changed, e.g. a new `ops.env` or checkout); `install.sh` on an installed machine brings it up with `radioctl compose up -d --no-deps scheduler`.
- **Dry run switches:** the scheduler reads an optional `runtime/scheduler.env` (`env_file`, `required: false`), the counterpart of the systemd drop-ins of the Windows dry run; `radioctl-ops`, `install.sh`, and `update.sh` pass `DRYRUN_CERTS` besides the `RADIOCTL_*` switches.
- **Docker versions on Linux and macOS:** `radioctl`'s preflight accepts Engine and Compose at or above the pin (`PLATFORM_DOCKER_PIN=min`; Windows stays exact). Without it decision 6 (any other distribution with Docker at least at the pin) could never pass the preflight. Ubuntu 24.04 and Debian 12/13 are still pinned and held by `install.sh`.
- **`first-run --backup-copy-dir <path>`** (empty: no copy) writes `BACKUP_COPY_DIR`, as `--media-root` writes `MEDIA_ROOT`; `.env.example`'s Windows default would otherwise warn on every backup.
- **`install.sh`** is the POSIX entry (root via `sudo`, the switches kept through `env`; macOS stops with "U4"); the Linux part is `install/install-linux.sh` (bash), because it reuses `install/lib/host-setup.sh`. Options: `--media-dir`, `--backup-copy-dir`/`--no-backup-copy`, `--repo`, `--branch`, `--yes` (no questions of its own; the first run's three credentials are still read from the terminal or standard input). The folders default to the existing `.env`; on an installed machine an option that differs from `.env` stops ("edit `.env`").
- **`host-setup.sh` for a Linux host** (Windows defaults unchanged, `tests/distro` green): `radio` with any free uid (uid 1000 is usually the administrator on a server, and renaming the stock `ubuntu` user would lock a cloud VM's admin out); no one-time `apt-get upgrade`; an existing different `/etc/docker/daemon.json` kept with a warning (the stack sets its own log rotation); the apt source and key URL parameterized (`ubuntu noble`, `debian bookworm|trixie`), the Debian versions derived as `ops/build.sh` does. `scripts/check-versions.sh` checks all five packages for noble arm64 and Debian 12/13 (amd64, arm64).
- **Folders:** the media folder is created if missing and gets the group `radio-media` with group write and setgid folders, recursively (asked; `--yes` does it); the second copy is created (owner `radio`, 0700) with a warning when it is on the same disk as `/srv/radio/backups`.
- **The clone** is made by the ops image's git as `radio` (`safe.directory='*'`, a local repository mounted read-only for a test); when `install.sh` runs from the checkout itself it is not pulled (a running bash script must not change under it).
- **`update.sh`** runs `bin/radioctl-ops` directly as `radio`, else through `sudo -u radio`; test switches `RADIO_DEPLOY_DIR`, `RADIO_USER`.
- **`bin/radioctl-ops` and the first run:** it also mounts the first run's `--media-root` and `--backup-copy-dir`, because the first run writes `.env` inside the container; without that a media folder outside `/srv/radio` would be invisible to the first run, and the second copy to it and to the scheduler it starts.
- **The CI job** (`tests/linux-install/run.sh`, also runnable on a developer machine in a throwaway privileged Ubuntu container with systemd and Docker CE 28.5.2: `tests/linux-install/container.sh`): a rollback needs two releases, so it builds the backend and frontend twice from the same sources with `VERSION` 1.0.0 and 1.0.1 (different digests), pushed to a local registry; `release.env` (1.0.0) lives in a scratch Git repository of the checkout that `install.sh` clones; `RADIOCTL_NO_FETCH=true`, because the scratch origin is not mounted in the ops container; the stack uses `tests/dryrun/compose.override.yml` (the TLS test Icecast). It also covers U2's "done when" with a test crontab of every minute and a stop and start of the scheduler with `last_backup_utc` set 30 h back. The frontend is checked out at its default branch.

**After the Linux dry run (2026-11-14):**

- **B1, one pass on a fresh host.** The runbook's order (build the ops image, then `install.sh`) could not work: a fresh host has no Docker before `install.sh`. `install.sh` now builds `radio-atlantida-ops:local` itself with `ops/build.sh` after it has installed Docker, when `ops.env` has no digest and the image is missing (asked; `--yes` builds), and goes on; `RADIOCTL_OPS_IMAGE` still selects another image. It passes the resolved image to every `radioctl-ops` call it makes.
- **B2, `sudo update.sh`.** `sudo` resets the environment, so an exported `RADIOCTL_OPS_IMAGE` never reached `update.sh`. `bin/radioctl-ops` now uses the local build `radio-atlantida-ops:local` by itself, with a one-line notice, while `ops.env` has no digest and that image exists. The documented way to run `update.sh` is as the administrator without `sudo` in front (it switches to `radio` itself and keeps the switches); `sudo -E` with switches. The runbook (12.3), `install.sh`'s closing message, `update.sh`'s header, and `radioctl`'s hints on linux (the full path `<checkout>/update.sh`, a note under `--help`) say so.
- **B3, `radioctl-ops --help`** wrote `runtime/docker` and `runtime/scheduler.yml` before reading its arguments, so `ops/smoke.sh` failed for a user who could not write the checkout. `--help`/`-h` (before the command) now writes nothing; `ops/smoke.sh` says who runs it (not root, in the group `docker`).
- **Smaller ones:** two runs in the same second get their own run logs (`-1`, `-2`, created exclusively, as the dumps); the scheduler's refusal lists the five commands it allows; `host-setup.sh` no longer creates `/etc/radio-atlantida` and `/var/lib/radio-atlantida` on a Linux host (only WSL uses them: `host.env` and install.ps1's source copy; `setup-distro.sh` creates them); the old-volume probe and the first run's guard keep main's quiet `docker volume inspect` after the rebase.
- **OrbStack uptime (no switch).** A machine restart does not reset `/proc/uptime` (the OrbStack VM's), and the scheduler container cannot see the machine's PID 1, so a `RADIOCTL_UPTIME0` for it could only be a fixed number. `dry-run.md` §8.4 documents the result instead (no boot check, or `LATE` with a wide boot window) and runs the boot check by hand with `RADIOCTL_UPTIME0=$(ps -o etimes= -p 1)`, which `radioctl` already honours.

5. **Built** (5.3; the `macos` job not yet run on GitHub). CI: shellcheck, a launchd plist lint, and a Colima profile check only (GitHub's macOS runners have no nested virtualisation).

### 5.3 U4 as implemented (deviations, unverified parts)

Built on 2026-11-14 as code and tests, at the developer's request before the live-voice check that §9 item 3 put first: there was no Mac to run Colima on. Everything below is tested with mocks (`tests/radioctl/macos.bats`, bash 3.2) and by rendering on a Mac (`scripts/check-macos.sh`, CI job `macos`); none of it has run against a real Colima.

**What was built**

- **`install.sh` on a Mac** runs `install/install-macos.sh` as the installing user, never as root (Colima and Homebrew refuse root); `sudo` only for `/opt`, `/usr/local`, the plist, `launchctl`, `pmset`, the journal owner, and the media group. bash 3.2 and BSD tools (no `set -E`: bash 3.2 runs an inherited ERR trap inside every failing command substitution). The Linux options all work (`--media-dir`, `--backup-copy-dir`/`--no-backup-copy`, `--repo`, `--branch`, `--yes`), with the same `.env`-wins rule. Idempotent: a second run reports no change, never restarts a running VM, never reloads an unchanged daemon.
- **Checks:** arm64 or x86_64; macOS 13+ (Colima's `vz`); 40 GB free on the disk of `/opt/radio-atlantida` for a first install (a warning on an installed Mac); a warning below 8 GB RAM.
- **Tools** (`install/versions-macos.env`, next to `install/versions.env` and apart from it so `install.ps1`'s comparison of that file is untouched): Colima 0.10.3, Lima 2.3.0, the Docker CLI 29.9.3, Compose 5.7.1, buildx 0.39.0 (buildx because `ops/build.sh` builds the ops image until it is published), per architecture with SHA-256 (GitHub's asset digests; the Docker CLI's computed from the download, Docker publishes none). Without Homebrew: the exact release files, checked, into `/usr/local` (`bin/`, `share/lima`, `libexec/lima`, `lib/docker/cli-plugins`); a tool at another version is replaced only on a yes. **Deviation:** with Homebrew the pins are minimums, not exact: Homebrew installs only a formula's current version, so the installer requires at least the pins and holds the formulae with `brew pin`; Homebrew's plugins are linked into `/usr/local/lib/docker/cli-plugins` (where the Docker CLI looks) instead of editing the user's `~/.docker/config.json`. `scripts/check-versions.sh` checks that every file hashes to its pin and that the CLI, Compose, and buildx versions equal the `install/versions.env` pins.
- **Colima's profile** `~/.colima/radio-atlantida/colima.yaml`: every key of Colima 0.10.3's template (checked against `tests/fixtures/colima-keys.txt`, which `check-versions.sh` compares with the upstream template), with `vmType: vz`, `mountType: virtiofs`, CPUs half the Mac's (at least 2) and memory half the RAM within 4–16 GB (the WSL rule of `install.ps1`), `disk: 100`, `autoActivate: false`, `sshConfig: false` (the user's `~/.ssh/config` untouched), `portForwarder: grpc` (below), `network.address: false`. Mounts at the same paths: the deploy folder, the data folder, the media folder, the second copy, and a local `--repo` (or the checkout's local origin) read-only; a folder inside another mount is not mounted twice. Started with `colima start --profile radio-atlantida --activate=false --save-config=false` (Colima keeps the file as written). A changed profile on a running VM is only a warning: it applies at the next start, in a maintenance window (runbook 13.3).
- **The Docker context is kept.** **Decision:** the station addresses the profile by its socket, `DOCKER_HOST=unix://$COLIMA_HOME/radio-atlantida/docker.sock` (`COLIMA_HOME` default `~/.colima`), in `install-macos.sh` after the start and in `bin/radioctl-ops` on every run (which also drops `DOCKER_CONTEXT`; `RADIOCTL_OPS_DOCKER_HOST` overrides for a test), not by the context name `colima-radio-atlantida`: the socket path is fixed by the profile name and needs no context metadata in the user's `~/.docker`, and it never touches the current context. Colima is told not to switch it (`autoActivate: false`, `--activate=false`); if it does anyway, the installer puts the context it found back.
- **The data folder.** **Decision:** `/opt/radio-atlantida/data` (`journal/`, `backups/`), next to `/opt/radio-atlantida/deploy` and `/opt/radio-atlantida/logs`, all owned by the installing user: `/srv` cannot be created on macOS (the system volume is read-only, only `/etc/synthetic.conf` could add it), and `/opt` can (Homebrew uses it). `radioctl-ops` mounts it instead of `/srv/radio` on macOS; the first run writes `PLAYOUT_JOURNAL_ROOT` and `BACKUP_ROOT` under it (`PLATFORM_DATA_ROOT`, `RADIOCTL_DATA_ROOT` for tests). The journal is owned by the pinned Liquidsoap image's user, as on Linux. The default media folder is `/Users/Shared/RadioAtlantida/media` (visible in Finder, not tied to one home).
- **Media folder.** **Deviation:** mounted **writable** into the VM, not read-only: the backend writes transcodes, fixed loudness, and replaced files next to the originals (6.6), so a read-only mount would break uploads. The ops container still mounts it read-only. As on Linux it gets the group 10001 with group write (asked; macOS needs no group entry for a numeric gid, and new files inherit the folder's group by the BSD rule, so no setgid).
- **Database (step 2):** the named volume `radio-atlantida-db` in Colima's VM, created by the installer and declared **external** in `runtime/host.override.yml` (`db.volumes: !override`, Compose ≥ 2.24), so `docker compose down -v` cannot remove it; `colima delete` still deletes it (runbook 13.5, "Never"). The name is deliberately not `radio-atlantida_pgdata` (the pre-6.11 Windows volume radioctl knows as the old one). `radioctl` adds the override to every compose call when `PLATFORM_DB_VOLUME` is set (macOS only) and stops when it is missing; the 6.11 guards of the directory and the old volume run only on wsl and linux; on macOS the volume itself is checked (missing: stop; used without `state.json`: stop at the first run); `status` shows `volume radio-atlantida-db in Colima's VM (...)`. `check-compose.sh` renders the override fixture (db's data is the external volume, nothing else changes).
- **Colima's engine version.** Colima 0.10.3's VM image brings Docker 29.5.2, below the pin 29.9.3 that `radioctl`'s preflight requires (`PLATFORM_DOCKER_PIN=min`). The installer runs `colima update --profile radio-atlantida` when the engine is below the pin (asked; `--yes`) and checks again. **Unverified:** which version `colima update` installs (Colima's newest from Docker's repository, not a pin).
- **launchd (step 1):** **Decision:** `/Library/LaunchDaemons/net.atlantida.radio.colima.plist` (root, 0644), `UserName`/`GroupName` the installing user and group, `colima start --profile radio-atlantida --activate=false --save-config=false` with `HOME`, `USER`, `PATH` (and `COLIMA_HOME` when set), `RunAtLoad`, `KeepAlive` `SuccessfulExit: false` with `ThrottleInterval` 60 (retried until it succeeds, e.g. a late external disk, but not restarted after a successful start), `AbandonProcessGroup` (the VM outlives `colima start`'s exit, and a reload never stops it), log `/opt/radio-atlantida/logs/colima-launchd.log`. Linted with `plutil -lint` before it is installed; loaded with `launchctl bootstrap system`, reloaded only when it changed.
- **pmset:** `sleep 0` and `autorestart 1` when they differ; a Mac that reports no `autorestart` (a laptop) gets a warning.
- **Core steps** as on Linux: the ops image (the local build while `ops.env` has no digest, in Colima's engine), the clone by the ops image's git into the existing (mounted) checkout folder, `radioctl network`, `radioctl first-run` or, on an installed Mac, the scheduler service; `ops/build.sh` now runs with bash 3.2 and skips `git rev-parse` on a Mac without the command line tools (its `/usr/bin/git` is an install-dialog stub).
- **`update.sh` (step 4):** the same file; on a Mac it runs as the checkout's owner (no user `radio`), directly when the caller is that user (no `sudo`), else through `sudo -u <owner> -H` (so `radioctl-ops` finds the owner's `~/.colima`); `COLIMA_HOME` is kept across it.
- **Live voice (step 3):** the default path only: `radioctl network` writes `127.0.0.1` (mode `local`, unchanged), the backend publishes `127.0.0.1:8189/udp` in the VM, and the profile uses Colima's **`grpc` port forwarder**, the one that forwards UDP (the default `ssh` forwarder forwards only TCP, and Colima marks `grpc` experimental). **Not built:** the fallback (network address mode and a NAT path for macOS in `radioctl network`); runbook 13.6 has the TODO and the check.
- **CI (step 5):** `scripts/check-shell.sh` covers the new files; job `macos` (macos-15) runs `scripts/check-macos.sh`: bash 3.2 and `sh` parse, `plutil -lint` and the keys of the rendered plist, the rendered profile through Ruby's YAML and the template keys, the host override; `macos.bats` (job `radioctl`) runs the installer under bash 3.2 from the official `bash:3.2.57` image with stubs of `colima`, `brew`, `launchctl`, `pmset`, `sysctl`, `sw_vers`, `df`, `docker`, `curl`, `shasum`, `plutil`, the real `sudo`, and checks the plist with `plistlib` and the profile with PyYAML.

**Unverified until the dry run on a real Mac (`dry-run.md` §9)**

## 6. Safety rules carried over

- Never run `docker compose down -v`, `docker volume prune`, `colima delete`, or remove `/srv/radio` (runbook "Never" box per platform).
- Updates never restart `db` or `liquidsoap` outside a maintenance window; the scheduler never runs `update`, `maintenance`, `cutover`, or `restore`.
- Secrets only in `.env` in the deploy folder (mode 0600, owner `radio` or the installing user); the ops container reads it through the same-path mount and never prints it.

## 8. Kubernetes later

The split maps directly: application services → Deployments/StatefulSet (PostgreSQL), `scheduler` jobs → CronJobs, `radioctl` steps → Jobs run from the ops image, `.env` → Secrets, `config/` → ConfigMaps, the bind mounts → PersistentVolumes.
